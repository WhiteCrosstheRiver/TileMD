# M5 — Cluster-pair tiles

## What is in

`src/neighbor/cluster_list.cpp` builds the column grid and the cluster-pair list on the host. Columns are an x–y grid with about 32 atoms each when the count is left at zero. Atoms in a column are stable-sorted by z and padded to a multiple of 8. Padding uses type `-1` and does not enlarge the bounding box. A pair of clusters is kept when the periodic box distance is below the reach. The shift index stores the image in `{-1, 0, 1}` on each axis.

`ComputeTileForces` evaluates full-list Lennard-Jones on that list, in cluster order, and writes forces back in the original atom order.

`src/md/tile_force.cu` runs the same pairs on the GPU. One warp owns one i-cluster. Lane `i_local + 8 * j_sub` holds i-atom `i_local` and, for each group of four j-clusters, the j-atom with that local index. The eight j-atoms are broadcast with warp shuffles, including the stored image shift. The four j-sub partials are added in order 0, 1, 2, 3. `HostSystem::use_cluster_tiles` sends `ComputeForces` and velocity Verlet down this path. The atom-neighbor engine stays the default. The cluster list is rebuilt on the host at every force call. Device thermo is not produced on the tile path.

## What was run

`BUILD_DIR=build-m8 bash scripts/check.sh` passed the CPU suite. The cluster-tile forces, energy, and virial match the double-precision oracle on `fcc_500`, `boundary_500`, `cutoff_500`, `twotype_2000`, and `melt_4000`. On the melt the force residual is `1.6e-12` against an rms of `24`.

The first efficiency numbers counted pairs from overlapping CSR rows. Columns were walked in `ix`, then `iy`, while clusters are numbered along the linear column index `ix + nx * iy`. A later row's start overwrote the previous row, so one cluster accumulated another cluster's pairs. Appending rows in cluster order removes that. The inside-pair counts now equal a direct pair loop: `27000` on `fcc_500` and `219324` on `melt_4000`.

Tile efficiency is pairs with `r < rc` divided by pairs the tile loop computes, with `rc = 2.5` and skin `0.3`:

| System | Pairs inside cutoff | Pairs computed | Efficiency |
|---|---:|---:|---:|
| `melt_4000` | 219324 | 2155574 | 0.102 |
| 32k LJ melt, initial dump | 1728000 | 18858752 | 0.0916 |

The plan expected about 40–60%. The corrected shortfall is still geometric. A column holds about 32 atoms, so an 8-atom cluster is a z-slice several cutoffs long. The bounding-box test keeps that whole slice, and most of its atom pairs are outside `rc`.

Changing the target occupancy to 64, 128, or 256 atoms per column does not close that gap. On every one of those grids the inside-pair count stays `27000` for `fcc_500` and `219324` for `melt_4000`, and the force residual stays at round-off, so the extra width is not a second copy of the same pairs. The best melt efficiency in the sweep is `0.108` at 128 atoms per column. At 256 it falls to `0.067`. The default remains about 32 atoms per column.

The GPU comparison `GpuLj.ClusterTileMatchesOracle` passed on the RTX 3050, and the forces match the oracle. The system in that test is a 12³ box. An 8³ box has only two cells at this cutoff and skin, and the engine rejects it before the tile kernel runs.

`GpuLj.TilePathRates` times `Run` on this RTX 3050. Clocks were not locked. Each rate is the median of three consecutive intervals after warmup. The atom-neighbor path is velocity Verlet with `graph_unroll` 50 and skin rebuilds. The cluster-tile path is the fused leapfrog with the same skin gate.

| System | Steps | Atom-neighbor | Cluster-tile |
| --- | ---: | ---: | ---: |
| 32k melt | 200, after 50 | 5.38e6 | 1.66e6 |
| fcc, ρ\*=0.8442, N=256000 | 50, after 20 | 8.49e6 | 2.48e6 |

The cluster-tile path is about 0.31× the atom-neighbor path at 32k and 0.29× at 256k, so the speed gate against M4 is not met. Both paths stay selectable. Nsight Compute profiled the first `TileForceKernel<0>` on the 32k melt: 4264 clusters, one warp each, 23.36 Mbyte of DRAM traffic (730 bytes/atom), 80 registers per thread, and 86% of peak SM throughput. Clocks were not fixed, and that launch is the forces-only kernel used before leapfrog, not the fused integrator. The text is `reports/profiles/M5/tile_force_32k.txt`.
