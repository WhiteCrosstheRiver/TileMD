# M6 — Fused single-kernel time step

## What is in

`reference/lj_reference.cpp` now steps the double-precision oracle with velocity Verlet, leapfrog, and BAOAB Langevin. Langevin draws three standard normals from Philox4x32-10 with counter `(gid, step low, step high, 0)` and key `(seed, 0)`. Zero friction calls velocity Verlet. Zero temperature multiplies the free-particle velocity by `e^{−γ t}`. The device kernel does not apply this thermostat. Leapfrog keeps `v(t − dt/2)`. The conversion from an integer-time start is `v(−dt/2) = v(0) − ½ dt f(0) / m`. Integer-time velocity for comparison is `v(t) = v(t − dt/2) + ½ dt f(t) / m`. Positions wrap into the box and image counters record the periods.

`RunFusedTileLeapfrog` is the GPU step used when `use_cluster_tiles` is set. One warp owns one i-cluster, as in the M5 force kernel. Pair coordinates are loaded from the current `pos4` buffer, rebuilt from the cell-local shadow, and promoted to double. The owning lane adds `dt f / m` to `v(t − dt/2)`, advances and wraps the double-precision `x`, and writes the other `pos4` buffer. The cluster list that selects those neighbors is still built on the host from the double-precision positions. The device copy is reused until `rebuild_every_step` is set or the maximum minimum-image displacement exceeds `(skin/2)^2`. The default of that flag is true, so a default run still rebuilds every step. The first `Run` converts `v(0)` with one force evaluation. The force array is not read during the fused step. On a thermo step the same kernel keeps the potential and virial and writes one partial per cluster. The kinetic energy is `½|v(t)|²` with `v(t) = ½(v(t−dt/2) + v(t+dt/2))`, the integer time of the positions the force used. A later one-thread kernel adds the partials into the thermo ring. After the last step, one extra force evaluation records that final integer time, because the positions have moved and the kernel that would see them has not run. Eight steps with an interval of 2 therefore record times 0, 2, 4, 6, and 8. On the CPU those potential energies, virials, and integer-time kinetic energies match velocity Verlet. Steps that are not thermo steps skip the energy and virial. The atom-neighbor engine still uses velocity Verlet, and this fused thermo path has not been launched.

## What was run

On 40 atoms, `dt = 0.005`, mass 1, for 100 steps, the CPU leapfrog and velocity Verlet stay within round-off. The largest position difference is `8.88e-16`. The largest integer-time velocity difference is `2.11e-15`. Image counters match.

On the 32k melt (`rc = 2.5`, skin `0.3`, 4264 clusters, 329108 cluster pairs) one fused step touches 69219396 bytes of distinct global addresses, 2163.1 bytes per atom. That count is the kernel's own loads and stores with the list already on the device: each real slot's `pos4`, each neighbor cluster's types, gids, and `pos4`, the CSR row, and the owning atom's double `x`, `v`, image counters, reference `pos4`, and the next `pos4`. Padding slots skip `pos4`. Four lanes that share one i-slot are counted once. It is not an Nsight `dram__bytes` measurement, and the kernel has not been launched. The §1.2 target of about 60–110 bytes per atom-step assumed the neighbor coordinates stayed on chip. They do not: about 9% of the visited pairs are inside the cutoff, and each kept cluster reloads eight `pos4` values. A rebuild also copies the list to the device, 91.3 bytes per atom on this configuration. The default `rebuild_every_step` flag does that copy every step.

When `rebuild_every_step` is off, `Run` captures `graph_unroll` fused kernels that alternate the two `pos4` buffers. A one-thread kernel writes the thermo step from the device counter before each fused kernel, so a thermo interval stays inside the graph. After each fused kernel the device replaces the cluster list only when the displacement is past half the skin. The column histogram and the column-key gather return immediately when the rebuild flag is clear. The column sort cannot see that flag, so it is captured in a conditional node. If that node cannot be captured, the sort stays in the graph and those early-exit kernels remain. The list is the one built before the capture until the skin trips. If the new list does not fit, the segment is restored and rerun one step at a time. The default still rebuilds every step on the host, so it does not capture the graph. On the CPU, that column sort matches the host grid, including a wrapped coordinate and a negative zero. A coordinate at z = −1 in a box of length 10 is stored in the box as 9, not as −1. The pair walk and the bounding box use the same functions as the host list, so the existing CPU list tests cover them. The GPU test that rebuilds a list on the device matches the host list on 64 atoms. A coordinate that wraps before the skin trips is put back on the reference branch before the stored image shift, so the pair vector stays the one from the rebuild. On the CPU a two-atom pair that crosses the boundary first still matches a rebuilt list exactly. The fused kernel rebuilds a coordinate from the cell-local shadow and calls that same branch function. Repeating the two-atom wrap on those float coordinates matches a rebuilt list with max `|dF|` = 0. One thousand leapfrog steps on the 40-atom box, rebuilding only past half the skin, do that rebuild 64 times and stay within `1.34e-11` of rebuilding every step.

`BUILD_DIR=build-m8 bash scripts/check.sh` compiles the fused kernel and passes the CPU suite. `GpuLj.DeviceClusterRebuildMatchesTheHostList` passed on the RTX 3050: 64 atoms, and the device list matches the host clusters, pair rows, and shifts.

`GpuLj.TilePathRates` is the speed comparison. On the 32k melt the fused `Run` reaches 1.66e6 atom-steps/s against 5.38e6 for the atom-neighbor engine. On the 256k fcc lattice the rates are 2.48e6 and 8.49e6. The fused path is slower, so the speed gate is not met. There is no separate M5 integrator to time against: `use_cluster_tiles` already runs this fused step. The forces-only tile kernel, profiled once on the 32k melt, moved 730 bytes/atom through DRAM and sat at 86% of peak SM throughput. That is above the 60–110 byte target and leaves little idle SM to recover. The fused kernel `TileForceKernel<1>` was profiled once on that melt, after skipping the forces-only launch. The grid is 32000 warps because the launch capacity is the atom count; warps past the live cluster count return immediately. DRAM traffic is 30.10 Mbyte, 941 bytes/atom, with 78 registers and 86% of peak SM throughput. Clocks were not fixed. The text is `reports/profiles/M6/fused_32k.txt`. The rate numbers above are from the run with no profiler attached.

`GpuLj.FusedLeapfrogMatchesTheCpuFor100Steps` launched the fused kernel on this RTX 3050. The system is a 5³ lattice, spacing 2.2, in a box of length 12. One hundred steps at dt = 0.005 move an atom by 0.013. Rebuilding every step, and the skin-gated path with `graph_unroll` 50, both match the CPU leapfrog. The skin-gated path launched two graphs of 50 steps; the displacement stayed inside half the skin, so the captured rebuild did not have to replace the list. The largest position difference is 2.75e-9 and the largest half-step velocity difference is 7.31e-9.

`GpuLj.FusedThermoMatchesTheCpuLeapfrog` runs the same lattice for 8 steps with `thermo_every` 2. The samples are steps 0, 2, 4, 6, and 8. Rebuilding every step and one captured graph of those 8 steps give the same gaps against the CPU leapfrog: potential energy 1.99e-7, kinetic energy 1.18e-10, virial 7.10e-7.

Rounding every coordinate to binary32 and promoting it back changes the melt force before the kernel runs. On `melt_4000` the relative force error against the double-precision oracle is `5.81e-5`. That is outside the T1 tolerance of `1e-5`. The same absolute rounding, after a shift of 256 (the binade of a box of length about 270), misses by `1.64e-3` and moves a coordinate by `1.53e-5`. `pos4` does not store that absolute value. xyz is the offset from a cell of edge 4, and w is the packed cell index. Rebuilding the shifted melt from that shadow misses the force by `9.14e-6` and a coordinate by `1.19e-7`. The force figure is inside T1. Because 256 is a multiple of the cell edge, those local offsets are the original melt coordinates modulo 4. The forces-only tile kernel still reads the double-precision slot coordinates. The fused kernel that reads the shadow is the 100-step launch above. The melt figure in this paragraph is still the CPU model of that rounding. On the 40-atom box the absolute rounding, used only for the force inside 100 leapfrog steps, moves positions by at most `5.69e-8`. The small box does not stand in for the melt.
