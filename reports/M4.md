# M4 — Performance foundation

## What landed

Neighbor rebuilds now stable-sort atoms by a 10-bit Morton code of the cell and permute every per-atom array. `gid` records the original index. Position, velocity, and force downloads scatter back to that index. Neighbors are sorted by global id, so the pair sum stays in the oracle's order.

`Run` sets `need_rebuild` on the device from a block-reduced minimum-image displacement, or from `rebuild_every_step`. The permute, cell-fill, and neighbor kernels return immediately when that flag is clear. `graph_unroll` steps are captured in one CUDA graph and replayed. The default is 50, which divides the 1000-step segment evenly. A request of 30 leaves a 10-step tail graph. The host synchronizes and reads `DeviceStatus` every 1000 steps. A device snapshot covers positions, velocities, images, types, and global ids; an overflow restores it, grows the list, recaptures the graph, and reruns the segment. Each step in the graph publishes `need_rebuild` to a conditional node whose body is the sort and the neighbor rebuild. If that node cannot be captured, the same kernels stay in the graph and return immediately when the flag is clear. Energy and virial run only when the completed step is a multiple of `thermo_every`. The reduction is a block sum followed by a single thread in block order, written into a device ring and copied out at the segment boundary. `ComputeForces` still sums on the host in global-id order. The force and neighbor kernels are `__launch_bounds__(128)` and read positions through `__ldg`. Pair parameters were already in constant memory. The force kernel is launched at block size 128. Sizes 64 and 256 were timed on this machine and were slower, so the integrator stays at 128. A non-finite force or position writes `emergency.extxyz` in original-gid order and aborts with the step and that atom's original id. That path has not been launched. When `dump_every` is positive and `dump_path` is set, the 1000-step segment stops at the next dump and `Run` appends an extended-XYZ frame in original-gid order. The fused path writes the stored leapfrog velocity. This dump has not been launched.

## Tests

`BUILD_DIR=build-m4 bash scripts/check.sh` compiled this engine, including conditional graph capture, and passed the two CPU tests (2026-10-19). The GPU suite was not repeated. The radial-distribution comparison has passed and the drift run has finished. The neighbor stencil was indexing a linear cell while the sort key was the Morton code, so `cell_start` was too short and the pairs were wrong. The stencil now uses that Morton code, and the array runs through the code of the last cell. `build-m8/tilemd_gpu_tests` then passed on this RTX 3050 in 152 s. That covers the seven fixtures, the shift dimer, a bitwise 10 000-step pair on `melt_4000`, the skin rebuild, overflow growth, and the 32k thermo comparison. The 32k means are potential energy −5.76748, kinetic energy 1.14814, and pressure 0.225424, the same samples as the earlier T3 table. The block-size sweep is below. An Nsight trace is still open, and there is no H100, A100, GPUMD, or LAMMPS-KOKKOS number, so G2 and G3 are not claimed. The earlier suite log is `reports/logs/stage1_gpu_check.log`.

## Block size

`GpuLj.ForceBlockSweep` on the RTX 3050. Clocks were not locked. Each force time is the median of three CUDA-event intervals of 40 launches, after one warmup launch and one neighbor build. The three sizes write the same float forces on the 32k melt. The full-step time is the median of three consecutive `Run(200)` intervals after a 50-step warmup, with the graph unroll left at 50. That is shorter than the §8 protocol (100 000 steps at 32k). 2M and 16M were not run.
